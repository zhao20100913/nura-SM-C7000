# 02 — GitHub Actions 构建

工作流：[`.github/workflows/build.yml`](../.github/workflows/build.yml)。
不需要 secrets 或自托管 runner：一切都在 `ubuntu-24.04` 上运行。

## 流水线做了什么

1. **检出**本仓库。
2. **释放磁盘空间**——runner 启动时约有 25 GB 可用空间，而镜像构建需要
   一个 chroot（约 2 GB）加上 rootfs 镜像（约 2 GB）。
3. **获取 pmbootstrap**，来源为 `https://gitlab.nura.eco/nura/pmbootstrap.git`，
   并把 `pmbootstrap.py` 软链接到 `/usr/local/bin`。
4. **获取 pmaports**（浅克隆 `main`，或手动运行输入中指定的分支），
   再把本仓库的 `pmaports/` 覆盖上去。因此我们的设备和内核包不会遮蔽上游的任何
   内容，它们只是作为新的 `device/testing/*` 包出现。
5. **写入 `~/.config/pmbootstrap_v3.cfg`**，其中包含 `device`、`kernel`、`ui`、
   `work`、`aports`、`jobs`、`service_manager=openrc` 以及镜像源部分。
   所有交互提示的默认值至此都有了答案，于是：
6. **`pmbootstrap init`** 以非交互方式运行（`yes "" | …`）；它会校验设备/内核
   的选择并完成初始化。

   `init` 还要求 pmaports 克隆中存在一个指向规范地址 `gitlab.postmarketos.org`
   的远端：它通过 `git show <remote>/main:channels.cfg` 读取 `channels.cfg`。
   由于我们的克隆来自 Nura 镜像，工作流会添加该远端，并把它的
   `refs/remotes/postmarketos/main` 指向我们检出的那个提交。
7. **预取内核源码**到 `$PMB_WORK/cache_distfiles`（在 chroot 内挂载为
   `/var/cache/distfiles`）。对于来自共享 runner IP 的匿名归档下载，
   `codeload.github.com` 会返回 `429 Too Many Requests`，因此该步骤带退避地
   下载，并用 `sudo` 安装文件（pmbootstrap 会把该目录创建为 root 所有）。
8. **`pmbootstrap checksum`** 为两个包重新计算 `sha512sums`。此时它发现
   tarball 已在磁盘上，因此只校验哈希——提交进仓库的哈希只是为了方便，
   CI 从不信任它们。
9. **`pmbootstrap build linux-postmarketos-qcom-msm8953-c7`** 先编译内核，
   这样有问题的 DTS 会尽早失败，而不是拖到最后。
10. **`pmbootstrap install --split --password 147147`** 构建 rootfs，使用
    OpenRC 并启用 SSH 守护进程（目前还没有显示，因此通过 USB 网络用 SSH
    是进入系统的途径）。`--split` 生成不带分区表的裸 ext4 rootfs，这正是
    可以写入 `USERDATA` 的内容。

    这里有两处变通，因为 GitHub 的 runner 需要它们：

    * **重试。** 在某些运行中，镜像*已完成*之后，清理阶段会以
      `umount: …/usr/bin/ qemu-aarch64-static: target is busy` 结束。
      该步骤用 `umount -l` 解除挂载、关闭 chroot 并重试一次；
      当两个镜像都已存在时，它也接受非零退出码。
    * **缓存。** `.pmb-work/packages` 和 `.pmb-work/cache_ccache_aarch64`
      由 `hashFiles('dts/**', 'pmaports/**')` 作为缓存键，内核源码 tarball
      有自己独立的缓存键。没有它们，每轮迭代都要付出完整的 40 多分钟
      内核交叉编译。
11. **`pmbootstrap export --odin`** 收集 `boot.img`、rootfs 镜像、Odin tar
    和各个 DTB；它们连同 `SHA256SUMS` 文件一起被复制到 `out/`。
12. **日志**（`$PMB_WORK/log.txt`）会被复制，构建产物通过 `if: always()`
    上传，因此失败可以直接在 Actions 页面上排查。

## 产物结构

```
nura-c7-<run>/
├── boot.img                 Android boot image (kernel + initramfs + DTB)
├── samsung-c7lte-root.img   ext4 rootfs (USERDATA)
├── samsung-c7lte.tar.md5    boot.img packaged for Odin (optional path)
├── dtbs/qcom/…              generated DTBs, for inspection
├── build.log                pmbootstrap log
└── SHA256SUMS
```

## 耗时与成本

| 步骤 | 典型耗时 |
| --- | --- |
| pmbootstrap init + checksum | 1–2 分钟 |
| 内核构建（qemu、LLVM） | 40–120 分钟 |
| rootfs 安装（console UI） | 10–20 分钟 |
| 导出 + 上传 | 2–3 分钟 |

公开仓库可以使用免费的 runner 分钟数；私有仓库会消耗账户配额（每次运行大约
60–150 分钟）。每周的 `schedule` 运行用于发现上游破坏——如果分钟数紧张，
把它停用即可。

## 调试失败的运行

- 打开 *Collect log* 步骤，从构建产物中下载 `build.log`；pmbootstrap 会打印出
  失败的软件包和最后 100 行日志。
- 红色的 *Build the C7 kernel package* 步骤几乎总意味着 DTS 语法错误。
  `./scripts/check-dts.sh` 只重新生成 dtc 所需的那几个文件（两个 SoC include
  加上 dt-bindings 头文件），并单独编译板级 dts，只需几秒钟，
  而不必来回等一轮 CI。在完整的主线源码树上，等价命令是
  `make ARCH=arm64 LLVM=1 qcom/msm8953-samsung-c7lte.dtb`。
- 节点体内的 `/delete-node/` 接受纯节点名
  （`/delete-node/ memory@10000000;`）；`&label` 引用只在 devicetree 层级被
  接受（`scripts/dtc/dtc-parser.y:239` 与 `:578`）。`&{/path}` 在这个 dtc 中
  两处都会被拒绝。
- 内核步骤为绿之后 *Build the image* 步骤又变红，通常是软件包依赖问题
  （`device-samsung-c7lte` 的 depends 列表）或缺少某个 `postmarketos-base`
  子包。

## 在本地运行同样的构建

在任意装有 Docker 的 x86_64 Linux 机器或常规发行版上：

```sh
git clone --depth=1 https://gitlab.nura.eco/nura/pmbootstrap.git
sudo ln -sf "$PWD/pmbootstrap/pmbootstrap.py" /usr/local/bin/pmbootstrap
git clone --depth=1 https://gitlab.nura.eco/nura/pmaports.git /tmp/pmaports
cp -a pmaports/. /tmp/pmaports/
pmbootstrap -p /tmp/pmaports init
pmbootstrap -p /tmp/pmaports install --split --password 147147
pmbootstrap -p /tmp/pmaports export --odin
```

（在本仓库所在的宿主机——一台 Android/bionic 设备——上，pmbootstrap 无法运行；
受支持的路径是 CI 流程。）
